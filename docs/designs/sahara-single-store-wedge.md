## Problem Statement

Small sellers sell through Instagram DMs and word of mouth: the catalog lives in
highlights, orders live in chat threads, payment gets chased manually. There is no
searchable catalog, no specs, no receipts, no order history. Sahara proposes a
beautiful storefront (Apple design system) where buyers browse, search, cart, order
and review, and where an admin self-manages items, specs, prices, images, banners
and discounts.

## Demand Evidence

**GATE NOT MET — this is the central open item of the doc.**
- Q1: founder recalled "a specific brand expressed real interest and asked when it ships."
- Q3 push: asked to name that person, founder answered "haven't named them yet — it's
  still vague in my head." The interest claim did not survive a specific question.
- No named seller, no payment, no demo feedback, no waitlist behavior. All six

## Status Quo

The sellers discussed have no real online presence: word of mouth + Instagram DMs.
Cheaper existing escapes: link-in-bio stores, WhatsApp Business catalog, Instagram
Shops, or Shopify — $0–30/month and launchable this afternoon. Why a seller would
choose Sahara over those is an assumption, not yet evidence.

## Target User & Narrowest Wedge

Target: one specific small seller/brand with a real catalog who currently takes
orders in chat. Not "brands" or "sellers" — a named human (to be supplied; see
Assignment).

Wedge (v1, Approach A — single store, one org):
- Buyer: browse/search catalog, product detail with specs + images, cart, checkout
  as an **order request** (no payment rails), order status, product reviews.
- Admin: register/login as admin of the single org; CRUD items with specs, prices,
  images/screenshots, storefront banner, and percent/fixed discounts; view orders
  and update status.
- Explicitly NOT in v1: multi-org self-registration, cross-brand search, payments,
  shipping rates, tax.

## Alternatives Considered

- **B — Full platform day one** (Postgres+Docker, true multi-tenancy, full discount
  engine, 2–3+ months): rejected — spending months replicating commoditized features
  before a single verified user (premises 2 + 6).
- **C — Inherit Medusa's commerce engine, own only the Apple storefront layer**:
  rejected for v1 — learning curve and framework lock-in outweigh saved CRUD while
  the build is still single-store. Revisit if A validates and cart/order engine
  complexity becomes the bottleneck.

## Chosen Approach — A: single-store wedge, local-first

Every feature the founder originally listed still exists in the schema; only the
scope (one org) and payment rails are deferred. `org_id` sits on every tenant table
from migration #1, so escalating to a marketplace later is additive, not a rewrite.

### Stack

- **Next.js 16 (App Router) + TypeScript**, React Server Components, server actions —
  pinned to latest stable at scaffold (16.4.2 at review time; D8).
- **Tailwind CSS + a custom Apple-HIG component layer we own**: SF-style type scale
  on `-apple-system` stack, frosted `backdrop-blur` navigation, iOS-like sheets,
  toasts, switches, segmented controls. No third-party component library — the
  design system is the differentiator, so it lives in our repo.
- **Drizzle ORM (pg-core)** — schema and migrations from migration #1; **Postgres in
  local Docker** for dev and CI (one-time env fix: add user to `docker` group);
  hosted deploys later change only the connection string (D7). Zod schema validation
  at every server action boundary.
- **Better Auth (stable 1.7.x)** — credentials provider; roles `user | admin`;
  DB-backed sessions carrying `org_id`; built-in rate limiting on register/login/
  checkout (D3, D10).
- **Single pricing engine `lib/pricing.ts`** — discount evaluation + order snapshots
  shared by cart, checkout and admin preview: one implementation, three callers
  (Code Quality F1).
- **StorageProvider interface**: `LocalDiskProvider` for product images/banners now,
  S3-compatible implementation later — call sites never change.
- **Money as integer cents everywhere**; price + discount **snapshotted onto
  order_items at order time** (historical pricing — long-term liability otherwise).
- **Orders**: status state machine (`placed → confirmed → fulfilled | cancelled`)
  with `order_status_history` rows (timestamp, actor, reason).
- **Search**: Postgres `ILIKE` substring over name + specs — advanced FTS engine
  deferred (D5; TODOS.md).
- **Discounts v1**: product-level percent/fixed with optional start/end dates,
  evaluated at cart time, snapshotted at order time.

### Data model (core tables)

`users(id, email, password_hash, role, org_id)` · `orgs(id, name, slug)` ·
`products(id, org_id, name, slug, description, price_cents, discount_type,
discount_value, discount_starts_at, discount_ends_at, stock_qty integer NULL =
unlimited/made-to-order, banner_path, active)` ·
`product_specs(product_id, key, value)` · `product_images(product_id, path, sort)` ·
`carts / cart_items(user_id, product_id, qty)` · `orders(id, org_id, user_id, status,
subtotal_cents, discount_cents, total_cents, placed_at)` ·
`order_items(order_id, product_id, qty, unit_price_cents, discount_cents)` ·
`order_status_history(order_id, from_status, to_status, actor_id, at)` ·
`reviews(user_id, product_id, rating, body)` unique per (user, product).
Indexes: `products(org_id, active)`, `products.slug`, `orders(user_id, status)`,
`order_items(order_id)`, `cart_items(user_id)`, `reviews(product_id)` (Perf F2).

### Flows

1. **Buyer**: home (banner + catalog) → search/filter → product detail (specs,
   images, review list) → add to cart → cart → checkout = order request → order
   status page → leave review after fulfillment.
   **Correctness contract (D11):** order placement runs in a **single DB
   transaction** (availability check → order + items insert → cart clear); stock
   decrement happens inside the admin confirm transition, restore inside cancel;
   illegal state transitions error instead of writing; server actions are
   idempotent against retries/double-clicks. Stock guard honors `stock_qty` null =
   unlimited (D9).
2. **Admin**: `pnpm seed` creates the single org + admin (D19) → dashboard →
   item CRUD with specs/images → set price & discount → banner management → order
   inbox → confirm/fulfill/cancel (history recorded; guarded transitions).
3. **Later (post-validation)**: org self-registration + cross-brand search unlock
   the original marketplace vision — schema already supports it via `org_id`.

### Flow diagram (checkout, D11 contract)

```
buyer            server action              Postgres
  │  click "Place"     │                        │
  ├───────────────────►│ BEGIN TX               │
  │                    ├───────────────────────►│
  │                    │ check stock (qty OK?)  │
  │                    │ insert order+items     │
  │                    │ clear cart             │
  │                    │ COMMIT ───────────────►│
  │◄─── order page ────┤ (on failure: ROLLBACK, │
  │                    │  show retryable error) │
  │  double-click ─────►│ idempotent key hit →   │
  │                    │ returns same order     │
```

### Order state machine

```
            [admin confirm]         [admin fulfill]
   placed ─────────────────► confirmed ────────────► fulfilled
      │                          │                      ▲
      │        [admin cancel]    │      [admin cancel]  │ (review allowed)
      └──────────► cancelled ◄───┴──────────────────────┘
   any other arrow / repeat transition = ERROR (no write, history untouched)
   confirm: stock_qty -= n (inside tx)   cancel: stock_qty += n (inside tx)
```

### Security (D10, D12)

- `requireAdmin` / `requireSession` **server-side guard wraps every admin server
  action and route** (defense in depth — not route-level only).
- Rate limiting on register/login/checkout via Better Auth's built-in limiter (D10).
- Zod validation at every server action boundary (restated here as commitment).
- Uploads: allowlist jpg/png/webp, 5 MB cap, max ~8 images/product + 1 banner,
  **generated UUID storage names** (user filenames never touch paths), requireAdmin,
  read-only serving (D12).
- DB-backed sessions (revocable) — no JWT-only authz.

### Configuration

`.env.example` committed listing: `DATABASE_URL`, `BETTER_AUTH_SECRET`,
`UPLOAD_DIR`, `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (D19), `SESSION_SECRET`.
No secret values in repo; dev values documented in the example.

### Error states (Section 1 F4 / Section 3)

- Postgres unreachable (container stopped/sleep): user-visible "retry" error state
  on every data page — never a blank render; covered by a test (mocked DB failure).
- Server-action failure: form-level error message with retry, inputs preserved.
- Upload rejection: inline message naming the violated constraint.

### Testing (D13, D14, D15)

- **Vitest** (unit/integration against a Postgres test DB) — pricing, state machine,
  repos, validation, stock guard.
- **Playwright E2E (all 5 flows)**: auth journey, browse→place order,
  double-click idempotency, admin confirm/cancel stock effects, requireAdmin denial.
- **CI**: GitHub Actions on PR — lint + Vitest + Playwright (built now, D15).
- **Token lint**: CI check that every primitive's styles resolve to `:root` variables (no raw hex outside `tokens.css`) — prevents token drift (eng re-run F2).
- Full artifact: `~/.gstack/projects/paramcodes-sahara/param-master-eng-review-test-plan-20261018-144647.md`
  (12 edge cases + 5 critical paths, value cards).

## Risks & Mitigations

- **Demand risk (primary)**: building on zero verified users. Mitigation: the
  Assignment below is a hard gate — no build start before it's met.
- **Commoditization**: every feature exists in Shopify/Medusa/Saleor. Mitigation:
  differentiation = design/taste + merchant experience, not features.
- **Local→Postgres drift**: mitigated by Drizzle dual-dialect from day one and
  running migrations against both in CI before the switch.
- **E-commerce invariants** (price snapshots, status history, integer money)
  adopted up front so the system doesn't rot the way the dev.to engineer's did.

## Design plan amendments (approved, apply at build)

### §A — Screen hierarchy (D21, Pass 1 → re-rated 6/10)

**Home `/` (PERSUADE surface):** (1) frosted sticky nav (wordmark / search / bag), (2) ONE full-bleed edge-to-edge lifestyle banner: brand, one headline, one sentence, one dark pill CTA — no cards, no inset/rounded variants, (3) quiet section heading, (4) product list as airy rows (thumbnail, name, price, discount badge) — NOT a card mosaic. One accent color (deep green) on #f5f5f7-style neutral. Hero budget enforced.
**Product `/product/[slug]` (convert):** (1) photo + thumbnails, (2) name/price/discount badge, (3) description, (4) specs table (hairline key/value rows), (5) qty stepper + full-width dark "Add to Bag", (6) delivery note, (7) Reviews. Utility copy only.
**Cart/checkout (operate):** line-item rows with hairline dividers + compact summary panel (subtotal / green discount line / total) + dark "Place Order" + reassurance line ("Pay on delivery — confirm by message").
**Admin (OPERATE surface):** slim sidebar (Products, Orders, Discounts, Reviews, Banner), landing on Orders inbox first (money first); products table = thumbnail/name/price/stock/status toggle; no card mosaics, minimal chrome.

### §B — Interaction states (D22, Pass 2 → re-rated 7/10)

Loading: skeleton shimmer on catalog/product/admin tables (NO spinners in content areas; spinner allowed inside buttons on submit only). Success: order placed → iOS-style success sheet with order number + "Track in Orders" CTA; review posted → inline toast; admin save → toast "Saved". Empty (warm copy + primary CTA each): empty catalog → "No products yet" (admin sees "Add your first product" onboarding row on first login — never a bare table); empty search → "No matches — try fewer words" + [Clear search]; empty cart → "Your bag is empty" + [Browse products]; no orders yet → "No orders yet"; zero reviews → "Be the first to review". Error: DB-down → retry error state (never blank); form → field-level message + retry, inputs preserved; upload reject → inline message naming the constraint. Partial: image loads but specs fail → page renders with specs skeleton replaced by "Details unavailable — retry" inline note; multi-upload partial-fail keeps successes, retries only failures. Uploads: determinate progress bar on each thumbnail.

> **Eng re-run amendment (D28/R11, 2026-10-18):** the product page composes three Suspense boundaries — images / summary+specs / reviews — each running one batched read (anti-N+1 preserved per section). Section-level failure renders the §B inline note without unmounting the rest. Catalog/home keep a single batched query.

### §C — Journey storyboards (D23, Pass 3 → re-rated 7/10)

Buyer (trust arc): 5-sec — lands on home, sees real banner + real prices + store wordmark (legitimacy check: "this is a real store, not a DM thread"); 5-min — browses specs, sees reviews and the "Pay on delivery — confirm by message" line, places first order (behavioral confidence; success sheet + order-status page carry it); 5-month — order history + reorder flow + review participation become the habit (reflective loyalty).
Seller (effort arc): minute 0 — seeded account, first login lands on Products with the "Add your first product" onboarding row (never an empty table); minutes 1-4 — add-product form on one screen, photo first, specs optional, price + stock inline; minute 5 — product live with "Live — share your store link". If this takes longer than 5 minutes, the seller is back in DMs: the form is the conversion funnel.

### §D — Anti-slop contract (D24, Pass 4 → re-rated 8/10)

Surfaces: storefront = PERSUADE shell over OPERATE catalog pages; admin = OPERATE. Hard rejections (all PASS, now intentional, not accidental): no SaaS card grid as first impression (§A list-rows); brand readable in banner; every CTA has a clear action verb; no busy imagery behind text; no repeated mood sections; no carousels; admin is table-first. Litmus: brand unmistakable in nav (YES); full-bleed banner anchor (YES); scannable headlines (YES via §A); one job per section (YES); no cards anywhere (YES — rows/tables only); motion: ONE authored entrance on the home hero (content fades/slides in once on load, ease-out, content-first — no scroll-jacking, respects prefers-reduced-motion) + hover states only where they carry information (row affordances); premium on flat fills (YES — frosted blur is a material, not decoration). Forbidden judgment tells (do not ship): gradient CTA buttons; hero metrics row ("10k happy customers"); glassmorphism ANYWHERE except the sticky nav's backdrop-blur; centered CTA pills with action-less labels ("Learn more"); stock-photo-feel banner (use the seller's real product photography); left-text/right-image split heroes; identical repeated section rhythms.

### §E — Apple token system (D25, Pass 5 → re-rated 8/10)

Commit as CSS variables (`:root`); no DESIGN.md exists so this section IS the token source of truth until `/design-consultation` produces one. Type — display/prices: SF-style stack (`-apple-system, "SF Pro Text", "SF Pro Display", system-ui` fallback chain, never bare `system`); body/forms/admin: Inter (explicit body/UI role, Operate allowance). Display ramp: 34/28/22 semibold (tight -0.02em); section 17 semibold; body 17/15; caption 13/11 regular. Two text faces max + tabular-nums for prices. Color: `--surface: #f5f5f7`-style neutral; `--ink` near-black; `--ink-2` secondary gray; `--accent` deep green (sole CTA/selection color); `--danger` red reserved for discount badges + destructive; hairlines `--line` 0.5pt neutral. NO flat single-color hero backgrounds; NO purple-on-white; one accent. Radius: sheets 10, pills 999, thumbnails 8 (no card radii ship — no cards ship). Spacing: 4pt grid, 16/24 section rhythm. Frosted nav: `backdrop-blur(20px) saturate(180%)` + hairline bottom border — the ONLY sanctioned glass (Pass 4). Focus: 2px accent ring, offset 2, always visible on keyboard nav. Motion: Pass 4 entrance only; `prefers-reduced-motion` disables it entirely (static hero). Primitives (own, dependency-free): Button(pill), Sheet, Toast, Switch, Stepper, Segmented, Badge, Skeleton, EmptyState — each spec'd by tokens above, nothing ad hoc.

### §F — Responsive & accessibility (D26, Pass 6 → re-rated 8/10)

Mobile ≤390px (primary surface): single column; catalog rows full-width (72px thumb, name+price stack); product page stacks image→summary→specs→reviews with a sticky bottom "Add to Bag" bar; admin tables scroll horizontally with sticky first column (never squished); nav collapses to wordmark + bag + search icon expanding inline. Tablet 768px: two-column catalog rows; product splits image/summary side-by-side at ≥900px. Desktop: max-width container, admin sidebar fixed. Keyboard: tab order = visual order; visible 2px accent focus (§E); Escape closes sheet/success states; steppers arrow-key operable; no keyboard traps. Screen reader: nav/main/footer landmarks; prices announced with discount context ("$40, was $50"); stock status as text, never color-only; tables carry captions. Touch: 44px minimum on ALL interactive elements including stepper buttons and dense admin row actions. Contrast: ink-on-surface and accent-on-white ≥4.5:1, verified with a check at build. Sticky bottom bars respect `safe-area-inset-bottom` and sit below sheets in z-order; skeleton shimmer is also disabled under `prefers-reduced-motion` (static placeholder) — eng re-run F3.

### §G — Pass 7 resolutions (D27)

Browse-CTAs ("Browse products", "Clear search" returns) anchor-scroll to the home catalog section (`id="catalog"`); no `/shop` route exists in v1. Banner source: the seller's own landscape banner photo is a seed-time requirement — T9's seed checklist gains "collect 1 landscape banner photo (real product/lifestyle, no stock)". Fallback if the seller misses it: compose the banner from the top 3 catalog product photos on the neutral surface with the headline overlaid (allowed: product-only composition, forbidden: stock-photo hero per §D).
